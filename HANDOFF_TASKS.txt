タスク2: breadth.json の同日重複エントリを解消する(append → 同日replace)
================================================================================
【背景】src/report/build_site.py :: update_breadth() は実行のたびに history へ
append する。ガード無効化中に1日最大5回実行された結果、2026-07-08 は同日12エントリ
など重複だらけになった。keep_days=60 は「約60営業日」のつもりが実質25日分しかなく、
ダッシュボードの地合いメーター履歴が歪んでいる。

【変更ファイル】src/report/build_site.py、tests/test_build_site.py(該当テストファイル名は
tests/ 内を grep で確認)、docs/data/breadth.json(既存データのクリーンアップ)

【手順】
1. update_breadth() を「同じ date のエントリが既にあれば置き換え、無ければ append」に
   変更する。実装例:
       breadth["history"] = [h for h in breadth["history"] if h.get("date") != date_str]
       breadth["history"].append(entry)
       breadth["history"] = breadth["history"][-keep_days:]
   (置き換え位置は末尾でよい。同日再実行は最新値で上書きが正しい挙動)
2. 既存の docs/data/breadth.json をワンショットでクリーンアップする:
   同一 date は最後のエントリだけ残す(dateの昇順は維持)。
   小さなPythonワンライナー/スクリプトで直接ファイルを書き換えてよい。
   クリーンアップ後のファイルもコミットに含める。
3. テスト追加: 「同じ日付で2回呼ぶと history は1件のまま・値は2回目のもの」を検証。

【受け入れ基準】
- update_breadth を同日2回呼んでも history の同日エントリは1件。
- docs/data/breadth.json に重複 date が存在しない
  (python で len(dates) == len(set(dates)) を確認)。
- pytest 全パス。

タスク5: 地合いシグナル(市場ブレッドス指標 + 攻め/中立/守りの3段階表示)
================================================================================
【背景】ユーザーの毎朝のルーティンは「地合い確認→銘柄チェック」。現在は指数カード・
テンプレ通過率・セクターマップを目視で総合判断しているが、1000銘柄の日足指標を毎日
計算しているのだから、ブレッドス指標を自動計算して信号機化できる。
市場が弱いときに新規エントリーを控えるのは SEPA の根幹なので、これは最重要機能。

【変更ファイル】src/report/build_site.py(または新規 src/report/market_signal.py を推奨)、
src/pipeline.py、docs/assets/app.js、docs/index.html、docs/assets/style.css、
tests/(新規テスト)、HANDOFF.md

【設計】
A. 毎日のパイプラインで以下のブレッドス指標を計算する(新規モジュール
   src/report/market_signal.py を作り、pipeline から呼ぶ):

   入力: latest_by_code (pipeline.run_daily 内で構築済み。各銘柄の最新行 dict で、
   close / ma50 / ma150 / ma200 / high_52w / low_52w / high / low カラムを含む。
   カラム定義は src/indicators.py を参照)

   - pct_above_ma200: close > ma200 の銘柄比率 (ma200 が NaN の銘柄は分母から除外)
   - pct_above_ma50:  close > ma50 の銘柄比率 (同上)
   - new_high_count:  high >= high_52w の銘柄数 (high_52w は当日を含む rolling max
     なので、等号成立 = 当日52週高値を付けた、とみなせる)
   - new_low_count:   low <= low_52w の銘柄数 (同上の理屈)
   ※ NaN 比較は False になるので pandas/純Python どちらでも素直に書けばよい。

B. 指数トレンド判定: TOPIX の日足終値系列から
   - src.data.indices の load_cache("topix") で parquet を読む(date, close のみ)。
     キャッシュが無い/短い場合は判定不能として None を返す(絶対に例外で pipeline を
     止めない)。
   - index_above_ma50 (bool), index_above_ma200 (bool), index_ma200_slope_up (bool:
     MA200の直近値 > 21営業日前の値) を計算。

C. 合成シグナル(判定ルール。config.yaml に閾値を追加して調整可能にする):
   config.yaml に新セクション:
       market_signal:
         green_pct_above_ma200: 0.50
         red_pct_above_ma200: 0.30
   判定:
   - "red"(守り):   index_above_ma200 == False、または pct_above_ma200 < red閾値
   - "green"(攻め): index_above_ma50 && index_above_ma200 && index_ma200_slope_up
                     && pct_above_ma200 >= green閾値 && new_high_count > new_low_count
   - "yellow"(中立): 上記以外
   - 指数判定が None(データ欠損)の場合は "yellow" とし、reason に「指数データ欠損」を含める。
   出力: {"signal": "green|yellow|red", "reasons": [人間可読の根拠文字列(日本語)],
          "pct_above_ma200": .., "pct_above_ma50": .., "new_high_count": ..,
          "new_low_count": .., "index_above_ma50": .., "index_above_ma200": ..,
          "index_ma200_slope_up": ..}

D. 保存先: update_breadth() の entry にこれらのフィールドをそのまま追加する
   (breadth.json の history に日次で蓄積され、履歴として追える)。
   update_breadth のシグネチャに market_signal: dict | None = None を追加し、
   None でないとき entry.update(market_signal) する形が既存流儀に合う
   (priority_counts と同じパターン)。

E. pipeline.py への組み込み: heatmap ブロックの後、update_breadth 呼び出しの前に
   try/except で計算(失敗しても本体を止めない。既存の heatmap/indices と同じ方針)。
   tests/test_pipeline.py の wired fixture にモック追加を忘れずに。

F. フロント(app.js):
   - initDashboard で breadth.json の最新エントリから signal を読み、ダッシュボード
     最上部(market-overview の上)に信号カードを表示:
     ・green: 「攻め」アクセント色 / yellow: 「中立」 / red: 「守り」danger色
     ・大きな色付きラベル + 根拠(reasons を箇条書き)+ 主要数値
       (MA200上回り率 xx% / 新高値 xx vs 新安値 xx)
     ・red のときは「新規エントリーは控えるのが原則」の注意文を出す
   - index.html にカード用のコンテナ追加、style.css にスタイル追加、?v=N 更新。

【テスト】
- market_signal.py の単体テスト: green/yellow/red の境界、指数データ欠損時 yellow、
  NaN銘柄の分母除外、new_high/new_low カウント。
- pipeline 経由で breadth entry にフィールドが載ることのテスト。

【受け入れ基準】
- pytest 全パス。

タスク6: ポジション管理(保有銘柄ビュー + 売りシグナル)
================================================================================
【背景】ツールは「エントリーするまで」しかカバーしておらず、エントリー後の保有銘柄
(現在R倍数、ストップまでの距離、売りシグナル)をユーザーが手計算している。
エグジット支援はワークフロー上いちばん大きい穴。

【入力の設計 — manual/positions.csv(新規)】
ファンダ手動入力(manual/fundamentals.csv)と同じ「手で編集するCSVをパイプラインが
読む」パターンを踏襲する。書き込みUIは作らない(現在 passkeyAuthEnabled: false で
書き込み系UIは全部killされている。ユーザーはGitHub web編集かローカル編集で行を足す)。

CSVスキーマ(1行=1ポジション。ヘッダ行あり):
    code,entry_date,entry_price,shares,initial_stop,current_stop,memo
    7203,2026-07-15,3500,100,3325,3325,VCPブレイク
- code: 証券コード(universe と同じ文字列型)
- entry_date: YYYY-MM-DD
- entry_price: 建値(円)
- shares: 株数
- initial_stop: 初期ストップ(R計算の分母。以後変更しない)
- current_stop: 現在のストップ(トレール時にユーザーが手で更新)
- memo: 自由記入(空可)
クローズしたポジションは行を削除する(履歴管理はスコープ外。memo欄で運用)。
サンプルとして manual/positions.csv をヘッダ行のみで新規作成しコミットする。

【バックエンド — 新規 src/report/positions.py】
1. load_positions_csv(): manual/positions.csv を読む。ファイルが無い/空なら [] を
   返す。パース不能行は警告リストに載せてスキップ(fundamentals.py の
   load_fundamentals_csv の流儀を参考に)。
2. build_positions_report(positions, indicator_by_code, name_by_code) -> dict:
   各ポジションについて、indicator_by_code[code] の最新行(close, ma50, ma200 等)から:
   - close: 現在値、pl_pct: (close/entry_price - 1)*100
   - pl_jpy: (close - entry_price) * shares
   - r_multiple: (close - entry_price) / (entry_price - initial_stop)
     (entry_price <= initial_stop の不正データは r_multiple: null にして警告)
   - dist_to_stop_pct: (close - current_stop) / close * 100
   - days_held: 営業日ではなく暦日でよい (today - entry_date).days
   - sell_signals: 文字列の配列。該当するものを全部入れる:
     ・"STOP_BREACH":  close < current_stop (ストップ割れ — 翌日成行で手仕舞い相当)
     ・"MA50_BREAK":   close < ma50 (50日線終値割れ — ミネルヴィニの主要売りシグナル)
     ・"MA200_BREAK":  close < ma200
     ・"TAKE_PROFIT_ZONE": r_multiple >= 2.0 (2R到達 — 一部利確/ストップ引き上げ検討)
     ・"BREAKEVEN_READY":  r_multiple >= 1.0 かつ current_stop < entry_price
       (1R到達したのにストップがまだ建値未満 — 建値ストップへの引き上げ検討)
   - code が universe/価格データに無い場合はレコードに "data_missing": true を付け
     数値は null(上場廃止・ユニバース外れ対応)。
3. 出力: docs/data/positions.json
   {"generated_at": ..., "warnings": [...], "positions": [...]}
4. pipeline.py への組み込み: indicator_by_code が完成した後(トレンドテンプレート
   評価の後ろでよい)、try/except で呼ぶ。失敗しても本体を止めない。

タスク7: ポジションサイジング計算機(個別株画面)
================================================================================
【背景】セットアップごとに risk_pct(買値〜ストップの幅%)は出ているが、「資金の
何%リスクで何株買うか」の最終計算をユーザーが暗算している。ここを自動化する。

【変更ファイル】docs/assets/app.js、docs/index.html、docs/assets/style.css
(バックエンド変更なし。純フロント機能)

【手順】
1. view-stock 内(#fund-detail-card の上あたり)に「ポジションサイジング」カードを新設:
   入力: 総資金(円)、1トレードあたりリスク(%。プリセットボタン 0.5 / 0.75 / 1.0 / 1.25)
   両方 localStorage("minervini_sizing_settings")に保存し次回から復元。
2. 対象銘柄の report.json レコードから buy_stop(買い逆指値)と stop_loss を取得。
   どちらか欠損(watchlist銘柄等)なら「セットアップ未確定のため計算不可」を表示。
3. 計算(riskPerShare = buy_stop - stop_loss):
   - 許容損失額 = 総資金 × リスク%
   - 理論株数 = 許容損失額 / riskPerShare
   - 発注株数 = floor(理論株数 / 100) * 100  ← 単元100株に切り下げ
   - 100株未満になる場合は「リスク許容内で1単元買えません(1単元の損失 = X円 =
     資金のY%)」と表示
   - 投入額 = 発注株数 × buy_stop、資金比 = 投入額/総資金
   - 資金比が25%超なら注意表示(ミネルヴィニの推奨ポジション上限20-25%。
     「1銘柄への集中が25%を超えます」)。50%超なら強い警告色。
   - 実損失額 = 発注株数 × riskPerShare も併記(切り下げでリスク%より小さくなる)
4. 表示は入力変更のたびに即時再計算(input イベント)。SPAの銘柄切替でリスナーが
   積み上がらないよう、既存流儀(btn.onclick 上書き or cloneNode差し替え。HANDOFF §7
   「SPA化に伴う再初期化の後始末」参照)に従うこと。
5. ?v=N 更新。

【受け入れ基準】
- buy_stop=2937, stop_loss=2797.44, 資金1000万円, リスク1% の場合:
  riskPerShare=139.56, 理論株数=716.5..., 発注株数=700株, 投入額=2,055,900円,
  実損失=97,692円 — この計算例で合っていることを確認。
- セットアップ未確定銘柄で「計算不可」表示。localStorage 復元動作。
- node --check 通過。目視確認内容を log.md へ。

タスク8: 簡易バックテスト(ブレイクアウト成功率の実績検証CLI)
================================================================================
【背景】rs_min 70 / breakout_vol_mult 1.4 / stop 5% 等のパラメータは一度も実績検証
されていない。また breadth.json の breakout_success_rate はセットアップがほぼ出ない
ため null が続いている(直近: 591銘柄中 actionable 1)。VCP検出が厳しすぎるのか
地合いのせいなのかを切り分けたい。data/prices/ に520営業日分の日足キャッシュが
あるので、過去データでイベントスタディができる。

【スコープを絞ること(重要)】完全なウォークフォワード(RSパーセンタイルの
point-in-time 再計算 + VCPの全日付スキャン)は計算量が膨大なので、フェーズ1として
以下の簡易版に限定する。これで「セットアップ検出頻度」と「ブレイク後の成績」の
実態が分かれば十分。

【新規ファイル】src/backtest.py(CLI: python -m src.backtest)
【変更ファイル】requirements.txt(追加不要のはず。pandas/numpyで完結させる)

【手順】
1. データロード: data/universe.json の銘柄について data/prices/{code}.parquet を読む
   (prices.py にロード関数があれば流用。無ければ pd.read_parquet 直読み)。
   ファイルが無い銘柄はスキップ。
2. 各銘柄に indicators.compute_all を適用(ベンチマーク無しでよい。rs_line 不要)。
3. RSの point-in-time 近似: 全銘柄の rs_raw を日付×銘柄の DataFrame にピボットし、
   各日付の行で rank(pct=True) → RS 1-99 に変換(indicators.rs_percentile_rank と
   同じ式をベクトル化)。これで「その日時点のRS」が全営業日分出る。
4. 検証ウィンドウ: 直近400営業日(パラメータ --days で変更可)。
5. VCPスキャンの近似: 全日付での evaluate_vcp 実行は重いので、週次(5営業日ごと)の
   日付グリッドで、その時点までのデータ(df.iloc[:i+1])に vcp_mod.evaluate_vcp を
   実行し、status=="WATCH_A" かつ contractions あり(=pivot 確定)のセットアップを
   記録する。同一銘柄で pivot が同じ(±1%以内)セットアップは1件に統合。
   ※トレンドテンプレート合格(その日のフラグ8条件、tt は latest 行でなく該当日の
   行で判定する関数を trend_template.py から流用/再実装)かつ RS>=rs_min の銘柄のみ
   スキャン対象にして計算量を削減する。
6. ブレイク判定: セットアップ記録後の日足を前進走査し、
   - close > pivot となった最初の日 = ブレイク日(60営業日以内に無ければ「不発」)
   - ブレイク日の volume/vol_ma50 >= breakout_vol_mult なら「強ブレイク」else「弱」
7. 成績測定: ブレイク日の翌日始値(無ければブレイク日終値)を仮エントリー価格とし、
   - ストップ: entry*(1-stop_loss_pct) を下回ったら損切り(終値ベース)
   - +5/+10/+20営業日後のリターン、最大ドローダウン、ストップ到達率
8. 出力: 標準出力にサマリー + data/backtest/backtest_YYYYMMDD.md にレポート保存:
   - セットアップ検出数(月別推移)← 「そもそもWATCH_Aが出ない」問題の定量化
   - ブレイク発生率、強/弱別の +5/+10/+20日 平均・中央値リターン、勝率、
     ストップ到達率、期待R
   - 主要パラメータ(rs_min, breakout_vol_mult, stop_loss_pct)を変えた場合の感度を
     見たいので、--rs-min/--vol-mult/--stop-pct をCLI引数化(既定値はconfig.yaml)
9. 注意: ルックアヘッドバイアスに気をつける(セットアップ判定に未来のデータを
   使わない。evaluate_vcp に渡す df は必ずその日までにスライス)。
   ユニバース自体の生存者バイアス(現在のユニバースで過去を見る)は既知の限界として
   レポート冒頭に明記する。
10. GitHub Actions 化はしない(ローカル/手動実行のみ。実行時間は数十分想定)。
    テストは軽量なユニットテスト(ブレイク判定・成績測定ロジックに合成データ)のみ
    でよい。フルバックテストの実行はユーザーのマシンで行う。

【受け入れ基準】
- 合成データのユニットテストが通る(ブレイク検出、ストップ到達、リターン計算)。
- 実データで少数銘柄に限定した実行(--limit 20 のような銘柄数制限引数を付けること)が
  完走し、レポートが生成される。
- pytest 全パス。実行方法と既知の限界を HANDOFF.md に追記。
